# rtemis news

## 1.3.2

- New algorithm: **SPLS**, Sparse Partial Least Squares via `spls`, for regression, binary and multiclass classification. Set up with `setup_SPLS()`; `k`, `eta` and `kappa` are tunable. `spls` takes no case weights, so `ifw = TRUE` aborts rather than fitting an unweighted model.
- New algorithm: **KNN**, weighted k-Nearest Neighbors via `kknn`, for regression, binary and multiclass classification. Set up with `setup_KNN()`; `k`, `kernel` and `distance` are tunable. `kknn` takes no case weights, so `ifw = TRUE` aborts, and it reports no variable importance, so `get_varimp()` returns `NULL`.
- `schema.rtemis.org` publishes both: `hyperparameters/spls/v1` and `hyperparameters/knn/v1`, each with its `record.json`, and both join the `algorithm` enum of the `hyperparameters` union - so their configs validate and describe like any other algorithm's.

## 1.3.1

- **Run records now state what the run scored.** A record already said how every tuning *candidate* performed and was silent on the model that was kept - so a model with good test performance and one with no generalizability produced near-identical documents. Two blocks close that. `metrics` and `metrics_sd` give each sample's headline row as a flat metric-to-value map, meaned across outer resamples with the spread beside it (`null` for a single fit, which has none), so `jq '.metrics.test.rsq'` answers "was this any good?" with no averaging and no R. Each entry of `folds` carries that fold's metrics in full - the confusion matrix in long form, the per-class rows - referencing the published metrics schemas, so a candidate's score and the final score are bounded by the same declarations.
- A fold's `tuning` block is now fully declared rather than an open object. It carries the candidate grid, each candidate's training and validation scores, and the winner, joined on `param_combo_id`; the score tables reuse the metric columns the metrics classes declare, so an out-of-range value or an undeclared column in a tuning table is rejected exactly as it is in a metrics block. Two shapes inside it have data-dependent keys and say so: a `param_grid` row and `best` are keyed by the hyperparameters being tuned, which cannot be declared without a schema per algorithm, so only the joining id is named and every other value is declared a scalar.
- `schema.rtemis.org` publishes the metrics classes: `regressionmetrics/v1`, `classificationmetrics/v1`, and their resampled counterparts. Unlike a config they have no `record.json` - they describe an output, which has no input counterpart to differ from - and they carry no `$schema` const, being produced by rtemis rather than authored against a schema.

- **Breaking change:** predicted probabilities are always a matrix. `Classification@predicted_prob_training` / `@predicted_prob_validation` / `@predicted_prob_test` were a plain numeric vector for binary outcomes and a matrix for multiclass, so anything reading them had to branch on the class count, and no schema could describe the field. They are now one row per case and one column per class, with binary carrying a single column - the positive class's probability, which is all any backend produces for that case - labelled with the class it holds. `predict()` on a `Classification` returns the same shape, since the two are the same quantity under two names. Code taking a single score per case (calibration, AUC, Brier score) should index the column: `mod$predicted_prob_training[, 1L]`.
- `to_json()` now emits exactly what the schemas declare. The default method walks a class's *published* properties, so a computed view (recoverable from other published fields) and an R-only value (a fitted backend model, a `sessionInfo()`) can no longer reach the wire undeclared. The hand-written `to_json()` methods for classification metrics are gone with it - the default now produces the same payload.
- `MetricsRes` and its subclasses are typed, completing the metrics work: per-resample metrics, and the mean and standard deviation across resamples, with the same bounded columns as a single sample's. A dispersion is bounded below by zero and not by the range of the values it summarizes, so a standard deviation is declared accordingly - R-squared is bounded above by 1 and unbounded below, and its spread across folds can exceed 1.
- `classification_metrics(sample = )` and `regression_metrics(sample = )` default to `NULL` rather than `character()`, and accept only the sample names rtemis uses. An empty vector was standing in for "unset", where `NULL` is the package's single unset value.
- Standard errors are computed on demand rather than stored. `Regression@se_training` / `@se_validation` / `@se_test` and the `RegressionRes` equivalents are removed, and `se(mod, newdata)` computes them from the fitted model instead. `se()` routes through the same pipeline as `predict()`, so a stored preprocessor or decomposition is re-applied before the backend is queried, and it returns `NULL` for an algorithm that has no standard error rather than failing. `to_json()` no longer reports `has_se`.
- Results-class properties that were `class_any` now are types. `Supervised@y_training` / `@y_validation` / `@y_test` are numeric or a factor, matching the predictions they are compared against (`SupervisedRes` holds one per resample, so those are lists); `@type` is one of `"Regression"` or `"Classification"`; and `SupervisedSession@started` / `@finished` are `POSIXct`. None of these classes generates a schema - the declarations are for type checking and validation, which is wanted everywhere, unlike JSON Schema generation, which is wanted only where something consumes it.
- New `prop_factor()` declares a factor-valued property. In R it is a distinct class, so a character vector assigned to a classification outcome is a type error rather than a silent loss of the level set. On the wire it is `{levels, codes}` - the levels in order, and a 1-based index into them per case - which is what every categorical type stores (an R factor, an Arrow dictionary, a pandas Categorical). An array of labels would not do: it loses the level *order*, which is what decides the positive class in binary classification, and any level with no cases. The schema asserts the 1-based indexing rather than leaving it to prose, since a 0-based reader would shift every label by one.

- **Metrics are typed.** `RegressionMetrics` and `ClassificationMetrics` declared their contents as a plain list or data frame, so nothing checked that a metric was a number, in range, or even present. Each now declares its tables with typed, bounded columns, validated on construction: a rate outside `[0, 1]`, an undeclared column, or a missing one is rejected with a message naming the field. A metric may still be `NA` where it is genuinely undefined (F1 when precision and recall are both zero, AUC when its backend fails) - that is distinct from a column being *absent*, which says the metric was not computed for this task at all. Which columns `overall` carries therefore still tells you what kind of task ran: three for multiclass, the positive class's rates for binary, and the probability-based pair when predicted probabilities were available.
- Per-class metrics now name their outcome level in a `level` column rather than in row names. Row names have no place in tabular output formats, so serialized metrics previously arrived without their labels; the column travels.
- A classification result's `positive_class` is now `NULL` rather than `NA` when the outcome is not binary. As `NA` the field was logical for multiclass and character for binary; `NULL` is the package's single "unset" value throughout, so test it with `is.null()`.
- A classification result's metrics now serialize on their own. `to_json()` previously produced a payload containing the raw confusion-matrix `table`, which `jsonlite` cannot serialize, so every consumer had to strip and convert it by hand; the payload now carries `confusion_long` instead and passes through untouched. The wire field is `confusion_long` with columns `reference`, `predicted`, `n` - matching the declared property - where the hand-written conversion had emitted `confusion` with `Reference`, `Predicted`, `Freq`, R's `as.data.frame()` defaults rather than a chosen vocabulary.
- `$` and `[[` on a metrics object now reach its properties as well as its metrics, so `metrics$confusion_matrix` returns the confusion matrix instead of `NULL`. New `confusion_long` holds the matrix in row-oriented form (`reference`, `predicted`, `n`), the shape a data frame reader expects, and is the declared, validated property: a confusion matrix's columns are the outcome levels themselves, so the wide form cannot be described by a fixed schema and cannot travel as a table. `metrics@confusion_matrix` is unchanged as a labelled `table`, derived from the long form on access, with both dimensions consistently named `Reference` and `Predicted`.

- New **run records**: every `train()`, `decomp()`, and `cluster()` call that is given an `outdir` now writes a `<prefix>.record.json` beside the saved model, stating what the run actually did. A record is the same field vocabulary as the config it came from, with three differences: every field is present and resolved (an unset one is written as an explicit `null`, so nothing falls back to a reader's defaults), each value is accompanied by an `origin` saying where it came from, and a `provenance` block records the rtemis and R versions, platform, timing, outcome, and a `DataFingerprint` of the data. `record(mod)` returns the same document as a list. Records are generated from the same property declarations as the configs, so `schema.rtemis.org` now publishes a `record.json` beside every `schema.json`, and each record is validated against its schema as it is written.
- `origin` distinguishes four ways a value reached a run: `user` (supplied), `default` (nobody chose it, including a *conditional* default such as LightGBM's `objective`, which follows from the task type), `derived` (computed from the data, such as the centering `preprocess()` learns or `feature_fraction`'s `sqrt(n_features)`), and `tuned` (selected by the Tuner from a search space). A fifth, `unset`, marks a field a failed or canceled run never reached. Which one applies is read from the declarations rather than guessed: a property marked `default_on_null` resolves to a task-type default, one marked `tunable` or `tune_on_null` to tuning. The published schema narrows the permitted origins per field, so it rejects a record claiming a user supplied GLMNET's `lambda.min`.
- A supervised record's top level is what was **asked for**; its `folds` array is what **ran**, one entry per model fitted. Outer resampling fits several models that resolve different values - early stopping settles on a different `nrounds` in each fold - so a single resolved value at the top level would state something no fold did. Each fold carries its resolved config with origins, and, when tuning ran, the parameter grid, the per-resample metrics, and the winning combination, so a tuning decision can be re-examined from the record alone. A single fit is one fold rather than a second shape.
- `Supervised` and `SupervisedRes` gain `@config`, `Decomposition` gains `@decompose_config`, and `Clustering` gains `@cluster_config`: the input each run was given. It is not derivable from anything else the object holds - the hyperparameters on a fitted model are the ones that *ran*, resolved - and a record needs both to say where each value came from. `read_config()` rejects a record fed where a config is expected, naming it, since a record's resolved values would otherwise silently pin settings the call should decide for itself.
- A fitted model now reports the values its algorithm resolved at train time. `train_()` receives its hyperparameters by value, so LightGBM's `objective`, LightRF's `feature_fraction`, LightGBM's `nrounds` and GLMNET's `lambda` were used for training and then discarded - `mod@hyperparameters` reported `NULL` for settings the model demonstrably used. The `train_()` methods that resolve a value now return it, and `train()` adopts it.

- The `.list_to_*()` reconstructors reject a key the target config does not declare, instead of silently ignoring it. A stale name, a typo, or a field belonging to another variant (`train_p` on a KFold resampler) is named in the error, with the nearest valid property suggested where there is one - `n` reports "did you mean `n_resamples`?". Previously such a key was dropped and the run proceeded with defaults, so a config could look accepted and train something other than what it asked for.
- Breaking change: `DecompositionConfig` and `ClusteringConfig` are reconstructed only from their canonical `{algorithm, config}` shape. A flat `{algorithm, k, ...}` was accepted by R but is rejected by the published schema, so accepting it took input the contract does not. Relatedly, `decomp(x, config)` now honors `config@features`: it validates the selection against the data and decomposes only those columns. Previously the field was ignored, so a config naming a subset fitted on *all* of `x` while `apply_decomp()` later subset new data to the named columns - the fitted object and its replay disagreed.
- Breaking change: `n_resamples` is declared per resampler type rather than once on `ResamplerConfig`. For every type but LOOCV it is ordinary configuration with a default of 10, so `{"type": "KFold"}` is now a valid config where it was previously rejected - matching the convention that an omitted field falls back to its `setup_*` default. For LOOCV it is run state written from the data, so a config supplying it is now rejected. This removes the last cross-field conditional from the published schemas.

- `setup_Preprocessor()` configs can be written and read: `preprocessor` joins the supported config families, with a new `.list_to_PreprocessorConfig()`. Map-valued properties (`scale_centers`, `scale_coefficients`) now serialize as JSON objects rather than arrays - `jsonlite` drops names on atomic vectors, so a named numeric emitted an array and failed the schema that declares an object.
- `data_dependent` is now a pure annotation. It marks a value whose shape follows one dataset (per-case grouping IDs, an initial embedding, per-feature centering), so a form should not prompt for it - and it no longer suppresses serialization. Every such property is a settable input, so `write_config()` dropping them lost values the user had supplied: `id_strat`, tSNE's `Y_init`, and DBSCAN's `weights` now round-trip.
- New declaration axes: `min_items` and `unique_items` constrain an array property's length and element distinctness (`DecompositionConfig@features` must name at least two distinct columns, previously enforced by a hand-written check and by the schema but not by the class); `default_on_null` marks a property whose `NULL` means "apply the default for this task type", the sibling of `tune_on_null`; and `prop_computed()` marks a derived view - a value that is a function of other published fields - which is omitted from schemas and from written configs rather than duplicated.
- `data_bound` gains `"numeric_feature_names"`, and `DecompositionConfig@features` declares it: an explicit selection must name numeric columns of the training data, replacing two hand-written checks in `train()` with one declaration that also reaches the published schema. `check_data_bounds()` now works with any config object rather than only `Hyperparameters`, and resolves only the dimensions actually declared, so `resample()` can enforce `id_strat`'s length without requiring a data frame.
- `Supervised@predicted_training` / `@predicted_validation` / `@predicted_test` are declared `class_numeric | class_factor` rather than `class_any`; `SupervisedRes`'s hold one element per resample and are `class_list`; and `CalibratedClassification`'s calibrated predictions are `class_factor`, being built by `prob2categorical()`.

- New `JSONSchema_to_S7()` builds a live S7 class from a JSON Schema generated by `S7_to_JSONSchema()`, completing the round trip: the reconstructed class carries the same types, bounds, enums, containers, and validators as the class the schema came from, and rejects the same values. Defaults and nested-config classes are supplied separately (`defaults`, `refs`) because neither is a schema keyword - the published tree carries no `default`, and a nested config appears as a `$ref` to its own schema - and the function names anything it cannot resolve rather than inventing a value. A new test round-trips every class in the package that declares its properties with the `prop_*` factories and compares them property by property.

- Breaking change: `algorithm` is gone as both a config property and a function argument. `train()`, `calibrate()`, `setup_SuperConfig()`, and `setup_SuperConfigLive()` no longer take it, and `SuperConfig` / `SuperConfigLive` no longer have it as a property. An algorithm is named exactly once, by its `setup_*()` function: `train(iris, hyperparameters = setup_LightRF())`, `calibrate(mod, hyperparameters = setup_Isotonic())`. This makes the `setup_*` family the single user-facing way to select an algorithm and configure it, removes the last argument that accepted case-insensitive names, and matches the published `supervised` schema, where the algorithm is the discriminator of the `{algorithm, hyperparameters}` union. `train(iris)` still defaults to Ranger. `decomp(algorithm = )` and `cluster(algorithm = )` are unchanged - there, `algorithm` is a real property of `DecompositionConfig` / `ClusteringConfig` - as is `draw_scatter(fit = )`, which selects a smoother.
- `setup_LightRF(feature_fraction = )` defaults to `NULL`, meaning "derive from the data" - `sqrt(n_features)/n_features` for classification, `0.33` for regression - resolved in `train()` where the data is known, as `objective` already was. Previously the class declared `0.7` while the path through `train(algorithm = "LightRF")` computed the data-derived value, so the effective default depended on which argument you used. The derivation is now stated in the property description and appears in the generated schema.

- Hyperparameter constraints that depend on the training data are now declared, not hand-written. A property whose valid values are tied to a dimension of the data says so at the declaration site with `data_bound = ` ("n_features", "n_cases", "n_classes", or "feature_names"), alongside its type, bounds, and enum. The check that applies follows from the property's existing `vector` flag: a scalar (e.g. Ranger's `mtry`) is bounded above by the dimension, while a vector-valued property (CART's `cost`, GLMNET's `offset`, Ranger's `case_weights` / `class_weights`) must have exactly that many values. `"feature_names"` (Ranger's `always_split_variables`) checks membership. `check_data_bounds()` resolves and checks them all in one pass, and generated schemas append the constraint to the property's description, since JSON Schema cannot express it structurally.
- New internal generic `validate_hyperparameters(hyperparameters, x)` runs those checks. `train()` calls it twice: once before any tuning or outer resampling, where a tunable hyperparameter still holds its whole search space, and again immediately before the algorithm runs, where the feature count reflects preprocessing and decomposition. The default method covers every `data_bound` declaration, so most algorithms need no method of their own; GLMNET has one because `penalty_factor` is bound to the design-matrix width rather than the feature count (factors expand to dummy variables).
- Every data-dependent hyperparameter is now checked against the data before any model is fit: `setup_CART(cost = )`, `setup_GLMNET(penalty_factor = , offset = )`, and `setup_Ranger(mtry = , case_weights = , class_weights = , always_split_variables = )`. An out-of-range value aborts immediately, naming the value and the dimension it must match. Because the check runs ahead of the tuning grid, a bad value is reported once, as itself, rather than as a run of failed or quietly dropped tuning cells; and because it runs again after preprocessing, a value that only becomes out of range once features have been transformed is caught there too.

## 1.3.0

- All configuration classes - execution, preprocessing, resampling, tuning, hyperparameters, clustering, decomposition, and the pipeline recipes - now declare their user-settable properties through the `prop_*` factories (`prop_boolean()`, `prop_integer()`, `prop_float()`, `prop_string()`), completing the rollout begun in the hyperparameter classes. Each such property carries a `PropertySpec` recording its type, bounds, enum, nullability, and description, so type checking, validation, and JSON Schema generation all derive from a single declaration instead of being written three times. Runtime and fitted-model properties (e.g. `Supervised@model`) keep their plain `class_*` declarations.
- Optional (nullable) properties now enforce that `NULL` is the only "unset" value: a nullable property is declared `NULL | <class>` so S7 prototypes it to `NULL` rather than the base class's empty vector, and a zero-length value reaching validation is rejected with a corrective message (`must not be empty (use NULL to leave it unset)`). This keeps every downstream `!is.null()` guard meaningful.
- Properties that are *not* user-settable configuration now say so at the declaration site, completing the picture above. `prop_state()` marks run state written during training or tuning (GLMNET's `lambda.min` / `lambda.1se`, LightGBM's `nrounds` / `best_iter`): never schematized, never serialized, re-derived on read. `prop_external()` marks a genuine config input whose R type the `prop_*` factories cannot express (tSNE's `Y_init`, Ranger's `inbag`, TabNet's `optimizer`, `id_strat`, the preprocessor's learned scaling values), optionally `data_dependent` when the value is tied to a particular dataset and so has no portable form. `prop_role()`, `role_prop_names()`, and `data_dependent_prop_names()` read them back.
- New `S7_to_JSONSchema()` generates a JSON Schema directly from an S7 class, `S7_dispatcher_JSONSchema()` composes leaf schemas into a discriminated-union dispatcher, and `write_JSONSchema()` serializes a schema to file. These generate the `supervised`, `hyperparameters`, `resampler`, `decompose`, and `cluster` schemas consumed by the rtemis CLI and rtemis.server.
- `S7_to_JSONSchema()` derives which properties take part from those roles instead of an `exclude` list: the `exclude` argument is replaced by `base`, naming the family base class whose inherited properties are machinery rather than config. A property declared `prop_external()` must have its schema fragment supplied via `extra`, which is now checked - previously a forgotten fragment silently dropped a key from the published contract. A property with no declared role remains an error. The generated schemas are unchanged.
- `setup_Preprocessor(impute_type = )` takes the full set of choices (`"missRanger"`, `"micePMM"`, `"meanMode"`) as its default and matches on them, as the other enumerated setup arguments do, so the choices are visible in the signature and to callers that introspect formals.

## 1.2.8

- New `session_timeline()` flattens a `SupervisedSession` execution graph into a timeline (Gantt) table -- one row per node in depth-first order with millisecond offsets, status, and tooltip text. It is the shared source for rtemis.draw's `plot()` method on `SupervisedSession` and rtemis.server's `job.result` `session` slice (rtemislive Timeline tab). `session_kind_colors()` (internal, exported) provides the matching fixed kind → color map so all renderers color steps identically.
- Progress reporting now uses `rtemis.core::progress_lapply()` (new in rtemis.core 0.4.0) instead of `cli::cli_progress_along()` in `train()` outer resampling, sequential `tune_GridSearch()`, and `massGLM()`. Nested runs render a single breadcrumb status line (`Outer resamples 2/5 › Tuning 7/30 ETA 0:41`) with a color-pulsing spinner, and emit structured `level = "progress"` envelopes through the rtemis.core message sink for `rtemis.server`. The **cli** dependency is dropped.
- Parallel tuning now reports progress through the same system: new `handler_rtemis()` bridges progressr `progression` conditions (relayed by future from workers) onto the rtemis progress renderer, and `tune_GridSearch()` wraps its future backend in `progressr::with_progress(handlers = handler_rtemis(...))` - previously, worker ticks were silent unless the user had activated progressr handlers themselves. The mirai backend polls task resolution and reports through the same renderer (replacing mirai's own cli collection bar).
- `train(dat)` defaults to ranger instead of throwing an error.
- `read` now uses preprocess to remove duplicates. renamed `make_unique` => `remove_duplicates`.
- Breaking change: New `apply_preprocessor(preprocessor, new_data)` applies a trained `Preprocessor` to new data and returns the preprocessed data directly, analogous to `predict()` for models. It replaces `preprocess(x, Preprocessor)`; `preprocess(x, config)` now accepts only a `PreprocessorConfig`.
- `preprocess()` now also accepts `setup_Preprocessor()` arguments directly for interactive use, e.g. `preprocess(x, scale = TRUE)`, creating the `PreprocessorConfig` internally. Calling `preprocess(x)` with no preprocessing parameters is an error.
